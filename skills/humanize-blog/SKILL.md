# 中文写作与文档去味指南

整体按真人平时跟熟手同事或朋友把事情讲明白的口气来写：自然、利索、偏口语一点，说人话，不要端公文和论文架子，不要满嘴极客黑话，也不要带 AI 客服腔。人称顺着场景自然用：写个人博客、随笔、踩坑复盘时尽量用第一人称“我”自然转述，少用“你、你们”居高临下说教；写团队分享或客观技术文档时直接拿具体模块、功能或操作做主语；任何场景都避开论文和公文里的“我们可以看到”“我们不难发现”。

**重要前提：克制和寡淡是两回事，活人感和装熟也是两回事。** 别为了避开套话把文字写成冷冰冰的机器速记或会议纪要，也别为了显得接地气在硬核内容里硬插俏皮话和自媒体词。哪怕是客观陈述或整理别人的技术演讲，也要像一个真的听懂了的活人在对面把逻辑讲顺，带出自然的语气重心（比如“哪怕……也得……”“本来就是……”“……是行不通的”）、详略轻重和说话人自己的判断。

## 先确认模式

动手前先判断当前任务属于哪一种：

- **润色 / 去 AI 味（用户给了草稿）**：保留原文的核心观点、事实细节、准确术语、代码结构和合理逻辑顺序，只调整表达、句式、标点和节奏。绝不编造原文没有的事实、数据或个人经历（比如擅自加上“我上周试了一下”），也不为了“通俗”把关键技术细节改歪或删掉。
- **从提纲、视频或素材整理起草**：直接从具体问题、结论、现象或真实场景切入，省掉宏大背景开场和“前半场讲 A、后半场讲 B”这类主持人报幕导语。允许篇幅有轻有重：真正有意思的核心部分放慢步子把直觉讲透，次要信息一两句带过，不要把每个小节、每个自然段写成一样长的压缩胶囊。如果篇幅较长，先在草稿里把干货和逻辑立住，再按下面细则通改一遍后输出。

## 去味细则

### 句式与节奏
1. **直接切入，砍掉头尾套话**：省掉“在……飞速发展的今天”这类宏大开场，省掉“好问题”“下面我将为你分析”这类客服前戏，整理视频/访谈时也省掉“问答环节干货密度一点不比正片低”这类报幕过渡。把话说完就结束，不用强行拔高升华，不搞复读式总结，也不用挂客套尾巴。
2. **避开套路转折、否定开头与自问自答**：少用排比，避开“不是……而是……”“并非……而是……”“不是……更像是……”“不是……真正要做的是……”“A 不等于 B”。不要用否定句开头（比如“这不是 xxx。它其实是 yyy。”），直接把后面真正想说的话写出来；也少用“那么问题来了”“这意味着什么？”“答案很简单”“听着挺反直觉的”这类自问自答和预告型转场。
3. **保留自然连接和呼吸感，不写电报体、压缩摘要和机械四拍子**：正常使用“如果、因为、所以、不过、哪怕、本来就”这些连接词和口语重心，别为了短促硬把连词砍掉，也别在正文里动不动用冒号写“先概括：再拆两句工整分说”的摘要压缩句（如“问题刚好倒过来：……”“仍然有用：……”）。不要一连写三四个长度差不多、结构对称、末尾还挂着四字成语的短句，不凑工整对仗和押韵金句（比如“A 定死了，B 却没封死”）。写多主题技术整理时，切忌每个小节都机械重复“传统方案痛点 → 新方案堆术语 → 贴图 → 夸一句很划算”的同一套四拍子，段落要有长有短，主菜展开讲透直觉，配菜利索带过。
4. **少用无灵主语和“进行/实现/完成 + 名词”**：少写“这一变化带来了……”“该机制有效解决了……”这类抽象无灵主语，也别把简单动词绕成“进行了重构”“实现了性能提升”“完成对配置的调整”，尽量用具体的人或事物做主语，直接用动词（如“重构了一遍”“把性能提上去”“改了下配置”）。

### 用词、语气与标点
5. **口语克制，警惕“表演型接地气”，也别滑回说明书**：口语化别用力过猛，不要写成公众号爆文或短视频解说。警惕这几类典型“演活人”词：
   - 表演感很重的夸张动词、叠词和自媒体夸赞词：“塞进去、严严实实、原封不动、彻底撑住、硬生生、榨干、玩出花、巧活、小魔术、花小钱办大事、干货、接地气、爽感、省工又提质、画风反差、贼整齐、一不做二不休、直接拉满”。
   - 用来硬凑聊天感的高频口头禅和万能副词：“说实话、老实说、讲真、不得不说、说白了”，以及满篇反复刷的“顺手”（一段接一段地“顺手传上、顺手画出、顺手做出”）。
   反过来也别一收就收成干巴巴的条款说明，该讲清体感、画面或原理直觉的地方自然展开半句，让句子落到地上。
6. **避开抽象大词、缓冲路标词和中度书面翻译词**：
   - 少用空泛抽象词：“本质、底层逻辑、维度、范式、生态、赋能、重塑、显著、系统性”。
   - 少用缓冲与机械路标词：“值得注意的是、换句话说、有意思的是、某种程度上、说到底、归根结底、总而言之、与此同时”。
   - 替换披着短句外衣的书面语和英文直译词：比如“从设计之初”“大致有迹可循”“暂停恢复”“有了替代品”“强度不会差得太远”，直接换成平时交流或该领域里真会脱口而出的活词（如“本来就是做出来让你……”“大概能摸清规律”“卡住不动”“有了差不多的顶上”“差不了多少”）。
7. **克制标点指纹、括号轰炸与正文乱加粗**：
   - 少用破折号（`——`）插话；不要给普通词乱加双引号表示强调或反讽（比如“隐性成本”“护城河”）；正文句子里少用 `**加粗**` 到处划重点。
   - **严控括号密度**：不要隔两句就用括号塞俏皮话或补充说明；技术文章不要给每个常见概念都机械加 `中文（English）` 注音（像 GPU、UV、Shader、UI、Boss 这类圈内直呼其名的词直接写，常见词如深度测试、阴影贴图直接写中文，只在读者可能需要搜论文或源码的关键专名首次出现时括注一次英文）。
   - **引用与视频时间戳别切碎句子**：整理视频或长资料时，不要每句话尾巴都挂一串 `（[01:30 xxx](url)、[01:52 xxx](url)）`，也不要写 `起/止` 这种机器索引符号。同一个连续片段合并成一处链接，放在段落末尾、小节起头，或自然挂在指代画面的短词上，让眼睛能顺畅读完一整段。
8. **语气统一，分清“脑补别人”和“表达自己”**：语气前后保持一致，不要前半句油滑吐槽、后半句突然文艺抒情。别用上帝视角替别人脑补心理活动（比如“他们心里也很清楚”“照样肯往里投心血”），客观讲对方说了什么、做了什么就行；引用别人的原话或原文句子时，直接加引号引出来，别硬揉进油腻的转述句里。不过**别为了客观把作者自己藏起来**，说话人自己的体感、判断和轻重侧重还是要留着，别把自己写成一个毫无感情的速记员。

### 结构、配图与立场
9. **有判断、少免责、少端水**：有明确判断就直说，不确定的地方直接交代不确定，别为了显得严谨隔三差五塞免责套话（比如“这不代表所有情况”“并非绝对如此”），有必要交代前提带一句就够了。少用“一方面……另一方面……”端水，也少用“就像给汽车装上发动机”这类廉价强行比喻。
10. **善用真 Markdown 结构，拒绝八股碎清单，杜绝“复读机图注”**：
    - **该用 Markdown 排清楚的地方主动用**，不要为了“防列表”把清晰的步骤和枚举压成一坨满是分号的长句：
      - **有序列表（`1. 2. 3.`）**：有明确先后次序的算法步骤、渲染/制作管线、操作流程（比如“生成分四步”“处理分三阶段”），直接用有序列表展开，别用“先……；再……；接着……；最后……”挤在同一段里。
      - **无序列表（`-`）**：明确的一组并列映射、分类规则、颜色或状态含义、参数项与工具清单（比如红/黄/绿三种网格属性、帧分析器三色条、时间轴两类事件标记）。项内直接说人话，条目名可用普通文字或行内代码，别每条都套 `**四字概括**：` 的 PPT 壳子。
      - **表格与行内代码**：2 个以上对象在多维指标上的横向对照用 Markdown 表格（不硬凑装饰性表格）；字段名、命令、事件名、数值区间用行内代码。
    - **该走自然段的地方走自然段**：讲观点、分析因果、叙事或转述对话时用有长有短的自然段，别把顺畅的逻辑强拆成满屏碎列表，别搞大段 `- **核心优势**：……`、`- **潜在风险**：……` 这种八股清单或强凑三点并列。
    - 标题和小标题直接说人话、讲清主题，别批量套用“具体现象，为什么……？”的设问模具，也别用“名词：短语 A，短语 B”强行把一整节关键词压进一行里。
    - **图文文章不要机械复读图注**：如果图片紧跟在已经把内容讲清楚的段落下面，直接放图即可，不要每张图底下都硬写一行 `*图注：……*` 把正文和图片 alt 换着词复读第三遍。只有多图对比需要指明“左/中/右分别看哪儿”，或者需要补充正文没写的时间戳和细节提示时，才配一行简短的看图线索。

## 改写对照

> 以下示例仅用于校准节奏和分寸，不要照搬里面的措辞和句式。

**例 1：去掉否定转折、抽象大词和强行金句**
- 改前：这并不是一次简单的工具升级，而是工作范式的底层重构。值得注意的是，真正拉开差距的，从来不是你用了多少工具，而是你是否具备“系统性思维”——工具定死了上限，思路却没封死。
- 改后：这次改动对日常工作流的影响比预想的要大。我用下来感觉，工具本身大家都能装上，最后效率差得多，主要还是看平时拆问题和整理上下文的习惯。

**例 2：收回过度口语化和上帝视角脑补**
- 改前：团队直接把旧代码原封不动地塞进了新框架，严严实实地撑住了第一波流量。他们心里也很清楚，这招短时间管用，但技术债早晚得还。
- 改后：团队先把旧代码直接迁到了新框架里，扛住了第一波流量。后来复盘时他们提到，这样做主要是为了赶上线时间，后面还得安排重构。

**例 3：拆掉宏大开头、八股清单和括号吐槽**
- 改前：在 AI 编程工具飞速发展的今天，我们在写提示词时往往会遇到两个痛点：
  - **规则过多**：上下文被撑爆，模型顾此失彼（没错，AI 也会健忘）。
  - **缺乏示例**：抽象描述难以对齐语气。
- 改后：平时写提示词，我踩过最多的两个坑，一个是规则堆太长，模型看不过来反而漏掉重点；另一个是光讲抽象要求不给例子，最后出来的语气总差那么一点意思。

**例 4：去掉“公文绕弯 / 说明书腔”，保留活人陈述感**
- 改前：这项限制生效后，旧习惯仍然有用：触发条件大致有迹可循，核心操作从设计之初就需要手动确认。另外，切换后台时所有计时都暂停恢复，切出去也等不来下一次刷新。
- 改后：这个限制加上以后，以前的经验还是能派上用场。什么时候会触发大概能摸清规律，关键那一步本来也就是做出来让你手动确认的。另外只要一切到后台，计时就会直接卡住不动，想切出去挂着等下一次刷新是行不通的。

**例 5：技术演讲笔记去括号轰炸、去“表演型口语”与复读图注**
- 改前：熔岩和河水常用速度图（Velocity Map）驱动纹理流动。最朴素的做法是纹理平流（Naive Advection），顺着流一会儿花纹就扯变形了（[01:30 扭曲](url)）。常规补救是**双层交替重置（Two Layers）**，可整片液面同频呼吸（[01:52 双层](url)）。GGG 在相位里掺了空间噪声（Phase / Time Noise），顺手打散了节拍（[02:27 噪声](url)）。
  *图注：从朴素平流拉丝，到双层交替重置，再到右侧加入噪声掩膜彻底打散肉眼可见的切换节拍*
- 改后：像熔岩、河水这类一直流动的表面，最直觉的做法是用一张速度图每帧推着 UV 走。但液面各处流速不同，有的地方散开，有的地方彼此错动，跑上几秒贴图就会被扯成细丝。常见补救是叠两层贴图交替重置：A 层流一小段就淡出归位，B 层错开半个周期接上。拉丝解决了，可整片岩浆同步一亮一暗，盯久了还是能看出节拍。Sannikov 的做法很干脆，在两层的混合相位里加了一层空间噪声——这边刚准备换层，隔壁那块已经换完了，局部照样在重置，整片看过去却找不到统一周期（[原片 01:30–02:45](url)）。

## 交付前自检

输出最终正文前快速扫一遍：
- [ ] 开头有没有宏大背景铺垫、客服前戏、主持人报幕或否定句起手？结尾有没有强行拔高、复读总结或客套尾巴？有就直接删掉。
- [ ] 全文有没有漏网的“不是……而是……”、自问自答转场（“那么问题来了/这意味着什么”）、连串四字成语短句或对仗金句？
- [ ] 读起来是不是像公文、会议纪要或机器说明书？有没有滥用无灵主语、“进行/实现/完成 + 名词”、正文冒号总分压缩句，以及披着短句壳的书面翻译词？
- [ ] 口语化有没有过头，滑向表演型词汇（“小魔术/巧活/玩出花/贼/干货/爽感/顺手/硬生生/塞进去”）或“说实话/说白了/不得不说”口头禅？
- [ ] 标点和括号干不干净？有没有满屏 `中文（English）` 注音、句句挂时间戳括号、高频破折号 `——`、强调性双引号或正文到处 `**加粗**`？
- [ ] 结构有没有主次分明，Markdown 排版是否清爽好读？有没有把 3 步以上明确流程或清晰分类枚举用分号硬压成一整段长句，没改成有序/无序列表？反过来有没有把观点叙事硬拆成“加粗小标题 + 冒号”八股碎清单，或给每张图硬凑复读正文的图注？
- [ ] 如果是润色稿或演讲笔记，原文的事实、观点、数据、术语、图片路径和关键原片链接是否完整保留，有没有擅自替作者编造经历？
